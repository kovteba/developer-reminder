[#java-collection-framework-linkedlist]
====== LinkedList class
`LinkedList<E>` — це *двозв'язний список* (`doubly linked list`), що реалізує одразу `List<E>`, `Deque<E>` та `Queue<E>`. Забезпечує <<complexity-o1,O(1)>> вставку/видалення на обох кінцях, але <<complexity-on,O(n)>> доступ за індексом (жодного прямого стрибка до комірки, лише обхід по вузлах). Дозволяє зберігати довільні об'єкти включаючи `null`. Не є потокобезпечним. Ітератор — <<fail-fast,fail-fast>>.

.Ієрархія наслідування
[source,subs="normal"]
----
Object
└── AbstractCollection<E>
    └── AbstractList<E>
        └── AbstractSequentialList<E>
            └── LinkedList<E>
----

Реалізовані інтерфейси: `List<E>`, `Deque<E>`, `Queue<E>`, `Cloneable`, `Serializable`.

NOTE: [[java-collection-framework-linkedlist-no-randomaccess]]На відміну від `ArrayList`, `LinkedList` *не* реалізує `RandomAccess`. Це не недогляд, а чесний сигнал: доступ за індексом у зв'язному списку не є O(1), тому `Collections.binarySearch()`, `Collections.sort()` та подібні алгоритми автоматично перемикаються на `ListIterator`-based стратегію (O(n) послідовний прохід) замість index-based, коли бачать `!(list instanceof RandomAccess)`.

NOTE: `Serializable` — маркерний інтерфейс, який дозволяє перетворювати стан об'єкта в послідовність байтів для збереження чи передачі по мережі.

NOTE: `Cloneable` — маркерний інтерфейс, який повідомляє `Object.clone()`, що об'єкт дозволено безпечно копіювати, інакше буде викинуто `CloneNotSupportedException`.

[[java-collection-framework-linkedlist-node]]
.Внутрішня структура
[source,java]
----
public class LinkedList<E> extends AbstractSequentialList<E>
        implements List<E>, Deque<E>, Cloneable, java.io.Serializable {

    transient int size = 0;
    transient Node<E> first; // голова списку (може бути null, якщо список порожній)
    transient Node<E> last;  // хвіст списку (може бути null)

    private static class Node<E> {
        E item;       // значення елемента
        Node<E> next; // вказівник на наступний вузол
        Node<E> prev; // вказівник на попередній вузол

        Node(Node<E> prev, E element, Node<E> next) {
            this.item = element;
            this.next = next;
            this.prev = prev;
        }
    }
}
----

Кожен елемент — окремий об'єкт `Node` у купі; вузли *не лежать поряд у пам'яті* (на відміну від масиву `ArrayList`) — єдиний шлях від одного до іншого це йти по ланцюжку `next`/`prev`. Sentinel (dummy) вузли *не використовуються* — `first`/`last` можуть бути `null` для порожнього списку. `size` зберігається явим полем, а не рахується обходом, саме щоб `size()` лишався O(1).

[source]
----
Список [A, B, C, D]:

null ←─ [A] ⇄ [B] ⇄ [C] ⇄ [D] ─→ null
         ↑                 ↑
        first             last
----

[[java-collection-framework-linkedlist-modcount]]`modCount` (успадковане поле від `AbstractList`) збільшується при кожній структурній зміні: `add`, `addFirst/Last`, `remove`, `clear`, `addAll`, `removeAll`, `retainAll`. Не змінюється при `set()`. Ітератор фіксує `expectedModCount = modCount` при створенні; розбіжність при `next()`/`previous()` кидає `ConcurrentModificationException` — fail-fast, так само як у `ArrayList`.

[[java-collection-framework-linkedlist-abstract-sequential]]`LinkedList` наслідує `AbstractSequentialList`, а не `AbstractList` напряму. `AbstractSequentialList` реалізує `get(index)`, `set(index,e)`, `add(index,e)`, `remove(index)` через `listIterator(index)` — тому `LinkedList` отримує коректну реалізацію index-based методів без явного коду, просто наслідуванням. `ArrayList` натомість наслідує `AbstractList` і реалізує ці методи інакше — через прямий доступ до масиву.

[#java-collection-framework-linkedlist-class-constructors]
.Конструктори:
* `LinkedList()` — створює порожній список; `first`/`last` = `null`, `size` = 0. Жодна пам'ять під елементи не виділяється;
* `LinkedList(Collection <? extends E> c)` — створює список і послідовно додає всі елементи `c` через `addLast()`, зберігаючи порядок.

NOTE: На відміну від `ArrayList`, немає конструктора `LinkedList(int capacity)` — і не може бути. У зв'язного списку немає поняття "ємності": кожен елемент виділяється окремим об'єктом `Node` у момент вставки, наперед "зарезервувати" пам'ять для майбутніх вузлів неможливо.

[[java-collection-framework-linkedlist-add-method]]
[[java-collection-framework-linkedlist-link-impl]]
.addFirst / addLast — суть переваги LinkedList
[source,java]
----
private void linkFirst(E e) {
    final Node<E> f = first;                        // зберігаємо стару голову
    final Node<E> newNode = new Node<>(null, e, f);  // prev=null, next=стара голова
    first = newNode;
    if (f == null) last = newNode;                   // список був порожній — він же й хвіст
    else f.prev = newNode;                            // старій голові кажемо: твій prev = новий вузол
    size++;
}

void linkLast(E e) {
    final Node<E> l = last;
    final Node<E> newNode = new Node<>(l, e, null);  // prev=старий хвіст, next=null
    last = newNode;
    if (l == null) first = newNode;
    else l.next = newNode;                            // старому хвосту кажемо: твій next = новий вузол
    size++;
}
----

NOTE: Жодного обходу списку — лише переставляння 2-3 вказівників. Це і є ключова відмінність від `ArrayList.add(0, e)`, де вставка на початок вимагає `System.arraycopy` всього масиву за O(n).

[source,java]
----
LinkedList<String> list = new LinkedList<>(List.of("A", "B", "C"));
list.addFirst("X"); // [X, A, B, C] — O(1)
list.addLast("Z");  // [X, A, B, C, Z] — O(1)
----

[[java-collection-framework-linkedlist-add-index-method]]
.add(int index, E e) — вставка в середину
`add(index, e)` делегує в `AbstractSequentialList`, що отримує `listIterator(index)` (це вже <<complexity-on,O(n)>> обхід до потрібної позиції) і викликає `ListItr.add(e)`, який просто вставляє новий вузол *перед* поточним `next` — O(1) на саму вставку. Разом: <<complexity-on,O(n)>> traversal + O(1) вставка = O(n) загалом.

[[java-collection-framework-linkedlist-node-traversal]]
.node(int index) — оптимізований traversal
[source,java]
----
Node<E> node(int index) {
    if (index < (size >> 1)) {       // index < size/2 ?
        Node<E> x = first;
        for (int i = 0; i < index; i++) x = x.next;   // йдемо з голови
        return x;
    } else {
        Node<E> x = last;
        for (int i = size - 1; i > index; i--) x = x.prev; // йдемо з хвоста
        return x;
    }
}
----

Обирається ближчий кінець (`first` чи `last`), тому найгірший випадок — обхід до *середини* списку, ~n/2 кроків. Це все одно O(n), просто з меншою константою. `LinkedList` не реалізує `RandomAccess`, тому `listIterator(index)` для довільної позиції завжди платить цю ціну.

[[java-collection-framework-linkedlist-get-method]]
.get / getFirst / getLast
[cols="2,1,4", options="header"]
|===
|Метод |Складність |Коментар
|`get(int index)` |O(n) |`node(index).item` — traversal з ближчого кінця
|`getFirst()` |O(1) |Прямий доступ `first.item`, `NoSuchElementException` якщо порожній
|`getLast()` |O(1) |Прямий доступ `last.item`, `NoSuchElementException` якщо порожній
|===

WARNING: [[java-collection-framework-linkedlist-get-in-loop]]`get(index)` у циклі `for (int i = 0; i < list.size(); i++) list.get(i)` — це O(n²), а не O(n)! Кожен виклик `get(i)` — окремий обхід до `i`. На мільйоні елементів різниця з `for-each`/`Iterator` (O(n), кожен крок = один вузол) — секунди проти годин. Завжди використовуй ітератор або `for-each` для послідовного проходу `LinkedList`.

[[java-collection-framework-linkedlist-peek-poll-method]]
.peek/poll/element — три родини "не кидати виняток" vs "кидати"
[cols="2,1,3", options="header"]
|===
|Родина |При порожньому списку |Приклад
|`get.../element()` |кидає виняток (`NoSuchElementException`) |`getFirst()`, `element()`
|`peek...()` |повертає `null` |`peek()`, `peekFirst()`, `peekLast()`
|`poll...()` |повертає `null` (і видаляє, якщо є) |`poll()`, `pollFirst()`, `pollLast()`
|===

TIP: Обирай `poll()`/`peek()` замість `remove()`/`element()`, коли порожня черга — це нормальний стан програми (наприклад, воркер, що чекає на задачі), а не помилка. Це рятує від обгортання кожного виклику в `try/catch`.

[[java-collection-framework-linkedlist-remove-method]]
.remove(Object o) — пошук + unlink
[source,java]
----
public boolean remove(Object o) {
    for (Node<E> x = first; x != null; x = x.next) {
        if (o.equals(x.item)) { unlink(x); return true; }
    }
    return false;
}

E unlink(Node<E> x) {
    final Node<E> next = x.next, prev = x.prev;
    if (prev == null) first = next; else { prev.next = next; x.prev = null; }
    if (next == null) last = prev;  else { next.prev = prev; x.next = null; }
    x.item = null; // допомагаємо GC — прибираємо strong reference на значення
    size--;
    return x.item;
}
----

`removeFirst()`/`removeLast()` — O(1): вузол уже відомий (`first`/`last`), просто `unlink()` без пошуку. `remove(Object)`/`remove(int index)` — O(n): спочатку лінійний пошук (за значенням або traversal до індексу), потім `unlink()` за O(1).

[[java-collection-framework-linkedlist-removeif-method]]
.removeIf / clear
`removeIf(Predicate)` `LinkedList` *не перевизначає* — використовується типова реалізація з `Collection`: `Iterator` проходить список і викликає `it.remove()` для кожного елемента, що задовольняє умову. На відміну від `ArrayList` (де це критично — уникнути O(n²)), для `LinkedList` кожне видалення через ітератор і так O(1) (`unlink()` за вже відомим вузлом), тож окрема оптимізація не потрібна — сумарно O(n).

`clear()` проходить по всіх вузлах і обнуляє `item`, `next`, `prev` у кожного — щоб GC міг зібрати навіть ті вузли, на які випадково лишилось зовнішнє посилання (наприклад, застарілий `Node`, захоплений у лямбді чи іншій структурі).

[[java-collection-framework-linkedlist-contains-method]]
.contains / indexOf / lastIndexOf
Усі три — лінійний перебір вузлів з `equals()` (`indexOf` — з початку, `lastIndexOf` — з кінця, `contains` — до першого збігу). При `o == null` порівняння йде через `x.item == null`. Складність завжди O(n) — прямого шляху "перестрибнути" до значення немає, на відміну від `HashSet`.

[[java-collection-framework-linkedlist-sort-method]]
.sort(Comparator) — LinkedList не має свого TimSort in-place
`LinkedList` не перевизначає `sort()` — використовується типова реалізація з `List`: `toArray()` копіює всі елементи в `Object[]`, `Arrays.sort()` сортує масив (TimSort, стабільний), потім `ListIterator.set()` записує відсортовані значення назад по вузлах. Складність O(n log n) на сортування + O(n) на копіювання туди-назад, і додаткова пам'ять O(n) — на відміну від `ArrayList.sort()`, який сортує `elementData` in-place без зайвого масиву.

[[java-collection-framework-linkedlist-iterator-method]]
[[java-collection-framework-linkedlist-listiterator]]
.iterator() / listIterator() — двонаправлений ітератор
`listIterator()` повертає `ListItr` з полями `lastReturned`, `next`, `nextIndex`. `next()` рухається вперед через `next.next`, `previous()` — назад через `lastReturned.prev`, `set()` замінює `lastReturned.item`, `add()` вставляє вузол перед `next`. Усі операції — O(1), бо ітератор уже тримає посилання на потрібний вузол; єдина "дорога" частина — саме *позиціювання* ітератора на старті (`listIterator(index)` — O(n) traversal).

.ListIterator.add() — справжня O(1) вставка в середину під час обходу
[source,java]
----
LinkedList<Integer> nums = new LinkedList<>(List.of(1, 2, 4, 5));
ListIterator<Integer> it = nums.listIterator();
while (it.hasNext()) {
    if (it.next() == 2) {
        it.add(3); // вставляє "3" одразу після "2" — O(1), без повторного пошуку позиції!
    }
}
System.out.println(nums); // [1, 2, 3, 4, 5]
----

TIP: Якщо потрібно вставляти/видаляти елементи в довільних місцях *під час* одного проходу — це саме той рідкісний випадок, де `LinkedList` через `ListIterator` дійсно виграє в `ArrayList`: позиція вже "запам'ятована" вузлом, повторний traversal не потрібен.

[[java-collection-framework-linkedlist-descendingiterator-method]]
.descendingIterator() — обхід з кінця
[source,java]
----
LinkedList<String> list = new LinkedList<>(List.of("a", "b", "c"));
Iterator<String> desc = list.descendingIterator();
while (desc.hasNext()) System.out.print(desc.next() + " "); // c b a
----

Повертає адаптер над `ListItr`, що стартує з кінця і рухається через `previous()`. Так само fail-fast, як і звичайний ітератор.

[[java-collection-framework-linkedlist-spliterator-method]]
[[java-collection-framework-linkedlist-spliterator]]
.spliterator() — late-binding, погано підходить для parallelStream
`LinkedList.spliterator()` — *late-binding*: розмір фіксується не при створенні, а лише при першому `trySplit()`/`estimateSize()`. `trySplit()` для `LinkedList` неефективний — немає індексного доступу, тому поділ вимагає обходу до середини за O(n/2). Порівняно з `ArrayList.spliterator()` (поділ навпіл за індексами, O(1)) — `LinkedList` поганий кандидат для `parallelStream()`.

[[java-collection-framework-linkedlist-sublist-method]]
.subList(from, to) — view, але без офсетного прискорення
`subList()` успадкований з `AbstractList` і повертає `SubList` — live view (зміни видно в обидва боки, як і в `ArrayList`), але, на відміну від `ArrayList.SubList`, кожен виклик `get`/`set` на підсписку заново отримує `listIterator` й обходить вузли — офсет не дає random-access прискорення, бо його немає й в оригіналі. Створення view — O(1), але подальша робота з ним так само O(n) на операцію, як і з батьківським списком.

[[java-collection-framework-linkedlist-toarray-method]]
.toArray()
Проходить по всіх вузлах і копіює `item` у новий масив — O(n). `toArray(T[] a)` поводиться так само, як в `ArrayList`: якщо `a` замалий — повертається новий масив потрібного типу; якщо завеликий — `a[size]` встановлюється в `null` як маркер кінця.

[[java-collection-framework-linkedlist-clone-method]]
[[java-collection-framework-linkedlist-clone]]
.clone() — shallow copy
`clone()` створює новий порожній `LinkedList` і послідовно додає всі елементи через `addLast(x.item)` — O(n). Це shallow copy: нові вузли `Node` (нова структура зв'язків), але `item`-посилання вказують на ті самі об'єкти, що й в оригіналі. Зміна mutable елемента через один список буде видна через інший.

[[java-collection-framework-linkedlist-serialization]]
.Серіалізація
`writeObject()` записує `size`, потім кожен `item` від `first` до `last`. `readObject()` читає `size` і послідовно відновлює вузли через `addLast()`. Поля `first`, `last`, `size` позначені `transient` — самі об'єкти `Node` ніколи не серіалізуються, відновлюється лише послідовність значень (аналогічно до того, як `ArrayList` не серіалізує "порожню" частину `elementData`).

[[java-collection-framework-linkedlist-big-o-notation]]
[#java-collection-framework-linkedlist-class-big-o-notation]
.BigO notation для `LinkedList`
[cols="2,1,4", options="header"]
|===
|`addFirst(E e)` / `addLast(E e)`        |O(1)       |Переставляння 2-3 вказівників, без обходу
|`add(int index, E e)`                   |O(n)       |Traversal до index (O(n)) + вставка вузла (O(1))
|`addAll(Collection c)`                  |O(m)       |m — розмір колекції, кожен елемент через `addLast`
|`getFirst()` / `getLast()`              |O(1)       |Прямий доступ до `first`/`last`
|`get(int index)`                        |O(n)       |Traversal з ближчого кінця, у гіршому разі ~n/2
|`peek()` / `poll()`                     |O(1)       |Без винятку при порожньому списку (peek/poll)
|`removeFirst()` / `removeLast()`        |O(1)       |Вузол вже відомий, лише `unlink()`
|`remove(int index)` / `remove(Object)`  |O(n)       |Пошук/traversal (O(n)) + `unlink()` (O(1))
|`removeIf(Predicate)`                   |O(n)       |Iterator-based, кожне видалення O(1)
|`contains` / `indexOf` / `lastIndexOf`  |O(n)       |Лінійний перебір вузлів
|`sort(Comparator c)`                    |O(n log n) |Копія в масив → TimSort → запис назад через ListIterator
|`clear()`                               |O(n)       |Обнулення `item`/`next`/`prev` кожного вузла для GC
|`size()` / `isEmpty()`                  |O(1)       |Поле `size`
|`iterator()` / `listIterator()`         |O(1)       |Створення об'єкта ітератора (позиціювання окремо O(n))
|`descendingIterator()`                  |O(1)       |Створення, обхід далі O(n)
|`subList(from, to)`                     |O(1)       |Створення view; кожна операція на ньому — O(n)
|`toArray()`                             |O(n)       |Копіювання всіх `item` у новий масив
|`clone()`                               |O(n)       |Поверхнева копія через послідовні `addLast()`
|===

.Коли використовувати
Цю колекцію варто обирати, коли домінують операції на *краях* послідовності: `addFirst`/`addLast`/`removeFirst`/`removeLast` (Deque/Queue-семантика), і майже не потрібен доступ за довільним індексом. Якщо ж в процесі роботи передбачається часте звернення до елементів за індексом — краще `ArrayList`.

[[java-collection-framework-linkedlist-pitfalls]]
.Ітерація та видалення
[source,java]
----
LinkedList<String> list = new LinkedList<>(List.of("a", "b", "c"));

// НЕПРАВИЛЬНО — ConcurrentModificationException:
for (String s : list) {
    if (s.equals("b")) list.remove(s); // ❌

// ПРАВИЛЬНО і О(1) на видалення (вузол вже відомий ітератору!):
Iterator<String> it = list.iterator();
while (it.hasNext()) {
    if (it.next().equals("b")) it.remove(); // ✅
}
----

TIP: Видалення через `Iterator.remove()` у `LinkedList` — справжнє O(1): ітератор уже стоїть на потрібному вузлі й просто відриває його зміною вказівників сусідів, без пошуку. Це дешевше за `list.remove(object)`, яке спочатку шукає вузол за O(n).

.Споживання пам'яті — Node overhead
[source,java]
----
// ArrayList<Integer>, 1_000_000 елементів:  ~4 MB (масив посилань) + самі Integer
// LinkedList<Integer>, 1_000_000 елементів: ~56 MB (Node ~40 байт кожен + Integer ~16 байт)
// LinkedList приблизно у 14 разів "важчий" за ArrayList для тих самих даних!

// Кожен Node<E>:
// - заголовок об'єкта JVM:  16 байт
// - item (ref):              8 байт
// - next (ref):               8 байт
// - prev (ref):               8 байт
// Разом: ~40 байт на вузол, ПОВЕРХ самого об'єкта-значення
----

WARNING: На практиці `LinkedList` майже завжди програє `ArrayList` за throughput навіть при частих вставках у середину — через cache miss: вузли розкидані по heap, CPU cache не допомагає, а `System.arraycopy` у `ArrayList` — надзвичайно оптимізована нативна операція. Завжди вимірюй (JMH), а не вгадуй, перед вибором `LinkedList`.

[[java-collection-framework-linkedlist-vs-arraydeque]]
TIP: Для Queue/Stack/Deque у новому коді майже завжди краще `ArrayDeque` — за бенчмарками у 2-6x швидший за `LinkedList` завдяки cache locality, відсутності Node-allocation overhead і бітовій арифметиці для wrap-around замість pointer chasing.

[source,java]
----
// LinkedList як Стек (LIFO):
Deque<String> stack = new LinkedList<>();
stack.push("first"); stack.push("second"); // addFirst
stack.pop(); // removeFirst → "second"

// LinkedList як Черга (FIFO):
Queue<String> queue = new LinkedList<>();
queue.offer("first"); queue.offer("second"); // addLast
queue.poll(); // removeFirst → "first"

// LinkedList як Двостороння черга:
Deque<String> deque = new LinkedList<>();
deque.addFirst("B"); deque.addFirst("A"); // [A, B]
deque.addLast("C");                        // [A, B, C]
deque.pollFirst(); // "A" → [B, C]
deque.pollLast();  // "C" → [B]

// Але для Queue/Stack у новому коді зазвичай краще:
Deque<String> faster = new ArrayDeque<>();
----

.Підсумки:
* Швидка вставка/видалення на обох кінцях за O(1) (`addFirst`/`addLast`/`removeFirst`/`removeLast`);
* Повільний доступ за індексом — O(n), а `get(index)` у циклі — прихована пастка O(n²);
* Не реалізує `RandomAccess` — алгоритми `Collections.*` самі це враховують;
* Значно більший memory footprint за `ArrayList` через overhead кожного `Node` (~40 байт/елемент);
* Дозволяє зберігати будь-які значення, включно з `null`;
* Не синхронізований;
* Для Queue/Stack/Deque у новому коді зазвичай кращий вибір — `ArrayDeque`.
