====== ArrayList vs LinkedList
`ArrayList` та `LinkedList` — дві найчастіше протиставлювані реалізації `List<E>`. Обидві мають однакову складність (Big-O) для більшості операцій "на папері", але зовсім різні внутрішні структури — суцільний масив проти двозв'язного списку вузлів — тому на практиці поводяться по-різному. Детальний устрій кожного класу описано у власних розділах (<<java-collection-framework-arraylist,ArrayList>>, <<java-collection-framework-linkedlist,LinkedList>>); тут — пряме порівняння віч-на-віч.

.Порівняльна таблиця
[cols="3,1,1,3", options="header"]
|===

.Доступ за індексом — код зсередини
[source,java]
----
// ArrayList — O(1):
return (E) elementData[index]; // прямий доступ до масиву

// LinkedList — O(n):
// мусимо пройти по ланцюжку вузлів до потрібного (з ближчого кінця, але все одно лінійно)
----

Перевагою `ArrayList` є доступ за індексом за <<complexity-o1,константний час O(1)>>, на відміну від `LinkedList`, який робить це за <<complexity-on,лінійний час O(n)>>. Виняток — доступ до першого й останнього елемента списку: він завжди O(1) в обох, бо `LinkedList` постійно тримає прямі посилання `first`/`last`.

.Доступ за значенням
Доступ до елементів за значенням (`contains`, `indexOf`) відбувається за <<complexity-on,лінійний час O(n)>> в обох реалізаціях — жодна структура не має "індексу за значенням", тому пришвидшити пошук самим вибором `List`-реалізації неможливо.

.Додавання елементів
Оскільки `LinkedList` постійно тримає посилання на перший і останній елемент, додавання в кінець або на початок не потребує пошуку і виконується за <<complexity-o1,константний час O(1)>>. Додавання у кінець `ArrayList` здійснюється за <<java-collection-framework-arraylist-class-add-big-o,амортизований константний час>>, але додавання *на початок* (`add(0, e)`) для `ArrayList` — це <<complexity-on,O(n)>>, бо потрібно зсунути весь масив. `LinkedList` може вставляти елемент у вже відому позицію (наприклад, через `ListIterator.add()`) за O(1) — саме вставка, без урахування часу на пошук цієї позиції.

.Видалення елементів
Видалення з *країв* `LinkedList` (`removeFirst()`/`removeLast()`) здійснюється за константний час — вузол уже відомий, просто переставляються сусідні посилання. Видалення з *довільної позиції* `ArrayList` (`remove(index)`) здійснюється за <<java-collection-framework-arraylist-class-remove-big-o,лінійний час O(n)>>, оскільки всі елементи після видаленого зсуваються вліво. `LinkedList.remove(index)`/`remove(Object)` теж O(n) загалом — сам пошук потрібного вузла лінійний, а от відривання знайденого вузла (`unlink()`) — O(1).

WARNING: `Iterator.remove()` під час ітерації — це якраз той рідкісний випадок, де `LinkedList` дійсно виграє: ітератор уже стоїть на вузлі, тому відривання — O(1), без пошуку. У `ArrayList` кожен `Iterator.remove()` все одно коштує O(n) через зсув масиву.

.Пам'ять: LinkedList vs ArrayList
[source]
----
ArrayList:  [A][B][C][D][_][_]  ← суцільний блок пам'яті
                                    (швидкий доступ, cache-friendly)

LinkedList: [Node:A] → [Node:B] → [Node:C] → [Node:D]
            розкидані по heap, кожен Node займає ~40 байт
----

`LinkedList` використовує більше пам'яті для зберігання тієї ж кількості елементів, оскільки крім самого значення кожен вузол зберігає ще два посилання (`prev`/`next`) і власний заголовок об'єкта JVM.

WARNING: Кожен `Node` несе накладні витрати: 2 посилання (16 байт) + заголовок об'єкта JVM (~16 байт) + саме значення. `LinkedList` також *недружній до CPU-кешу* — процесор не може завантажити сусідні елементи одним блоком, бо вузли фізично розкидані по heap. `ArrayList` на практиці швидший навіть там, де теоретична асимптотична складність однакова.

.RandomAccess і сортування
`ArrayList` реалізує `RandomAccess`, `LinkedList` — ні. Це впливає не лише на "філософію", а й на реальний вибір алгоритму: `Collections.binarySearch()`/`sort()`/`copy()`/`fill()` перевіряють `instanceof RandomAccess` і для `LinkedList` автоматично переходять на повільнішу `ListIterator`-based стратегію. Сортування (`list.sort(comparator)`) у `ArrayList` відбувається *in-place* прямо в `elementData`; у `LinkedList` — копіюванням у тимчасовий масив, сортуванням TimSort і записом назад через `ListIterator`, тобто з додатковою витратою O(n) пам'яті.

.subList — обидва live view, але не однаково дешеві
`ArrayList.subList()` повертає view, що зберігає офсет і користується прямим доступом до батьківського масиву — кожна операція на ньому коштує стільки ж, скільки на оригіналі. `LinkedList.subList()` теж live view, але без офсетного прискорення: кожен виклик `get`/`set` на підсписку заново запускає `listIterator` й обходить вузли — офсету не існує, бо його немає й у самого `LinkedList`.

NOTE: Обидва класи однаково не потокобезпечні, мають fail-fast ітератори (`ConcurrentModificationException` при структурній зміні поза ітератором) та однакову семантику `equals()`/`hashCode()` — обидві успадковані від `AbstractList` і порівнюють вміст поелементно з урахуванням порядку.

Загалом `LinkedList` в абсолютних величинах програє `ArrayList` як за споживаною пам'яттю, так і за швидкістю виконання більшості операцій — навіть тих, де асимптотика формально однакова, через локальність пам'яті та відсутність накладних витрат на об'єкти-вузли. `LinkedList` варто розглядати лише коли відбувається дійсно активна робота (вставка/видалення) на *краях* послідовності або в позиції, вже відомій через `ListIterator`, а не за довільним індексом.

.Коли використовувати LinkedList, а коли ArrayList
[cols="3,1,1", options="header"]
|===
|Критерій |`LinkedList` |`ArrayList`
|Вставка/видалення на початку   |✅ O(1)                     |❌ O(n)
|Вставка в кінець               |✅ O(1)                     |✅ O(1) amortized
|Пам'ять                        |❌ більше (Node overhead)   |✅ менше
|CPU cache                      |❌ поганий                  |✅ хороший
|Як Queue/Stack                 |✅ природно                 |❌ не призначений
|parallelStream() / Spliterator |❌ неефективний             |✅ ефективний
|===

TIP: *Використовуй `LinkedList`, коли:* потрібна черга або стек (хоча `ArrayDeque` зазвичай ще краще); дуже часто видаляєш/додаєш елементи на початку; ітеруєш список і видаляєш під час ітерації через `Iterator.remove()`.

TIP: *Використовуй `ArrayList`, коли:* потрібен частий доступ за індексом; більшість операцій — читання; важлива ефективність пам'яті; плануєш `parallelStream()`.

IMPORTANT: У переважній більшості випадків `ArrayList` швидший на практиці навіть там, де теорія каже, що складність однакова — через cache locality й відсутність Node-overhead. Переходь на `LinkedList` лише маючи конкретну, виміряну причину (профільований bottleneck на вставках/видаленнях по краях), а не "про всяк випадок".
