[#java-collection-framework-copyonwritearraylist]
====== CopyOnWriteArrayList class
`CopyOnWriteArrayList<E>` — це *потокобезпечний список на основі динамічного масиву* з пакету `java.util.concurrent`, що реалізує `List<E>`. Забезпечує <<complexity-o1,O(1)>> доступ до елементів за індексом і читання *без жодного блокування*. Головна ідея: будь-яка мутуюча операція (`add`, `set`, `remove`) під капотом створює *повну копію* внутрішнього масиву — тому читачі ніколи не блокуються і ніколи не бачать частково зміненого стану. Дозволяє зберігати `null`. Ітератор — *fail-safe* (не <<fail-fast,fail-fast>>): він працює над snapshot-ом і ніколи не кидає `ConcurrentModificationException`.

.Ієрархія наслідування
[source,subs="normal"]
----
Object
└── AbstractCollection<E>
    └── AbstractList<E>
        └── CopyOnWriteArrayList<E>
----

Реалізовані інтерфейси: `List<E>`, `RandomAccess`, `Cloneable`, `Serializable`.

NOTE: `CopyOnWriteArrayList` знаходиться у пакеті `java.util.concurrent`, а не `java.util`. Це єдиний потокобезпечний `List` у стандартній бібліотеці, чиї методи читання (`get`, `size`, ітерація) взагалі не використовують `synchronized`/`Lock` — вони лише читають `volatile`-посилання на поточний масив.

NOTE: [[java-collection-framework-copyonwritearraylist-randomaccess]]`RandomAccess` тут не косметика: попри "concurrent" у назві, доступ за індексом лишається справжнім O(1) `array[index]`, точно як у `ArrayList`. Копіюється весь масив лише при *записі*, а не при читанні.

NOTE: `Cloneable` дозволяє `Object.clone()` без `CloneNotSupportedException`; `Serializable` дозволяє серіалізувати список (записується лише поточний snapshot елементів, без `lock`/`volatile`-полів).

WARNING: [[java-collection-framework-copyonwritearraylist-write-heavy-warning]]`CopyOnWriteArrayList` *не підходить для частих записів*. Кожна мутація копіює весь масив — O(n) за часом і пам'яттю. Використовуй його лише коли читань на порядки більше ніж записів.

[[java-collection-framework-copyonwritearraylist-fields]]
.Внутрішній устрій
`CopyOnWriteArrayList` має мінімальну кількість полів:

[source,java]
----
public class CopyOnWriteArrayList<E>
        implements List<E>, RandomAccess, Cloneable, java.io.Serializable {

    final transient ReentrantLock lock = new ReentrantLock(); // захищає лише ЗАПИС

    private transient volatile Object[] array; // volatile — видимість між потоками БЕЗ synchronized
}
----

Два ключові механізми:

* `volatile` на `array` — гарантує, що всі потоки бачать *актуальне посилання* на масив без `synchronized`;
* `ReentrantLock` — захищає *запис*, дозволяючи лише одному потоку одночасно модифікувати список; читання лока не бачать взагалі.

[[java-collection-framework-copyonwritearraylist-modcount]]NOTE: На відміну від `ArrayList`/`LinkedList`, у `CopyOnWriteArrayList` немає поля `modCount` і немає fail-fast перевірок. Замість "виявляти й кидати виняток при паралельній зміні" архітектура просто *унеможливлює* конфлікт: читач тримає посилання на старий масив (`volatile` read), поки не прочитає нове; поточна мутація ніколи не змінює масив, який хтось уже читає.

[#java-collection-framework-copyonwritearraylist-class-constructors]
.Конструктори:
* `CopyOnWriteArrayList()` — створює порожній список; внутрішній масив одразу `new Object[0]` (жодного lazy init, на відміну від `ArrayList`);
* `CopyOnWriteArrayList(Collection <? extends E> c)` — копіює елементи `c` у новий масив через `Arrays.copyOf`. Якщо `c` вже є `CopyOnWriteArrayList` — масив береться напряму, без зайвого копіювання;
* `CopyOnWriteArrayList(E[] toCopyIn)` — копіює переданий масив через `Arrays.copyOf`; оригінальний масив користувача не змінюється і не використовується напряму.

[#java-collection-framework-copyonwritearraylist-class-methods]
.Методи:
* <<java-collection-framework-copyonwritearraylist-read-model,`get(int index)` / `size()` / `isEmpty()`>> — читання без будь-якого блокування;
* <<java-collection-framework-copyonwritearraylist-add-impl,`add(E e)` / `add(int index, E e)` / `set(int index, E e)`>> — мутація через copy-on-write під lock;
* <<java-collection-framework-copyonwritearraylist-addifabsent,`addIfAbsent(E e)` / `addAllAbsent(Collection c)`>> — атомарне додавання лише якщо елемента ще немає;
* `remove(int index)` / `remove(Object o)` / `removeAll(Collection c)` / `retainAll(Collection c)` — видалення елементів (копія масиву без них);
* `removeIf(Predicate <? super E> filter)` — атомарне видалення за умовою, одна копія масиву;
* `replaceAll(UnaryOperator <E> operator)` — застосовує оператор до кожного елемента, одна копія масиву;
* `sort(Comparator <? super E> comparator)` — сортує копію масиву й атомарно публікує її;
* <<java-collection-framework-copyonwritearraylist-snapshot-iterator,`iterator()` / `listIterator()`>> — fail-safe snapshot-ітератори, без `remove`/`set`/`add`;
* `subList(int start, int end)` — view на *snapshot*, а не на живий список;
* `toArray()` / `toArray(T[] array)` — копія поточного внутрішнього масиву;
* `contains(Object obj)` / `indexOf(Object obj)` / `lastIndexOf(Object obj)` — лінійний пошук по snapshot, без блокування;
* `clear()` — атомарно замінює масив на `new Object[0]`;
* `clone()` — поверхнева копія: новий список з копією поточного масиву.

[[java-collection-framework-copyonwritearraylist-read-model]]
.Як працює читання — повністю без lock
[source,java]
----
public E get(int index) {
    return elementAt(getArray(), index); // getArray() → volatile читання
}

final Object[] getArray() {
    return array; // volatile read — завжди бачимо останній опублікований масив
}
----

Читач завжди бачить *консистентний snapshot* масиву. Якщо запис відбувається паралельно — читач бачить або старий масив, або новий, але *ніколи не частково змінений*.

[[java-collection-framework-copyonwritearraylist-add-impl]]
.Як працює copy-on-write при add(E e)
[source,java]
----
list.add("D");
// До:    array → ["A", "B", "C"]
// Після: array → ["A", "B", "C", "D"]  (новий масив!)
//                ["A", "B", "C"]        (старий масив — читачі, що взяли його раніше, продовжують бачити саме його)
----

[source,java]
----
public boolean add(E e) {
    synchronized (lock) {
        Object[] es = getArray();          // беремо поточний масив
        int len = es.length;
        es = Arrays.copyOf(es, len + 1);   // копіюємо з +1 місцем — O(n)
        es[len] = e;                       // додаємо елемент у кінець копії
        setArray(es);                      // volatile write — публікуємо нову копію
        return true;
    }
}

final void setArray(Object[] a) {
    array = a; // volatile write — всі потоки одразу бачать новий масив
}
----

NOTE: `volatile write` у `setArray` є *happens-before* бар'єром: усі зміни у новому масиві гарантовано видимі іншим потокам одразу після того, як вони прочитають нове посилання.

`set(index, e)`, `remove(index)`, `sort()`, `removeIf()`, `replaceAll()` — та сама схема: захопити `lock` → взяти поточний масив → зробити копію потрібного розміру зі зміненим вмістом → `setArray()`. Різниця лише в тому, *як саме* формується нова копія (з елементом у кінці, без елемента на позиції, відсортована тощо).

[[java-collection-framework-copyonwritearraylist-addifabsent]]
.addIfAbsent — атомарна перевірка і додавання
[source,java]
----
CopyOnWriteArrayList<String> set = new CopyOnWriteArrayList<>();
set.addIfAbsent("A"); // → true,  список: ["A"]
set.addIfAbsent("B"); // → true,  список: ["A","B"]
set.addIfAbsent("A"); // → false, список: ["A","B"] (не змінився)
----

[source,java]
----
public boolean addIfAbsent(E e) {
    Object[] snapshot = getArray();
    return indexOfRange(e, snapshot, 0, snapshot.length) < 0  // перевірка БЕЗ lock
        && addIfAbsent(e, snapshot);                           // copy ПІД lock
}

private boolean addIfAbsent(E e, Object[] snapshot) {
    synchronized (lock) {
        Object[] current = getArray();
        if (current != snapshot) {          // масив міг змінитись між двома перевірками
            int common = Math.min(snapshot.length, current.length);
            for (int i = 0; i < common; i++)
                if (current[i] != snapshot[i] && eq(e, current[i])) return false;
            if (indexOfRange(e, current, common, current.length) >= 0) return false;
        }
        Object[] newElements = Arrays.copyOf(current, current.length + 1);
        newElements[newElements.length - 1] = e;
        setArray(newElements);
        return true;
    }
}
----

NOTE: `addIfAbsent` використовує *double-check*: спочатку перевіряє без lock (оптимістично), потім знову під lock (захищено, бо масив міг змінитись між двома перевірками). Це зменшує contention у типовому випадку, коли елемент уже є.

[[java-collection-framework-copyonwritearraylist-snapshot-iterator]]
.Snapshot-ітератор — чому немає ConcurrentModificationException
[source,java]
----
CopyOnWriteArrayList<String> list = new CopyOnWriteArrayList<>(List.of("A", "B", "C"));

Iterator<String> it = list.iterator(); // бере snapshot: ["A","B","C"]

list.add("D"); // інший потік — список тепер ["A","B","C","D"]
list.add("E"); // ще один запис          ["A","B","C","D","E"]

while (it.hasNext()) {
    System.out.println(it.next()); // A, B, C — без D і E!
}
----

[source,java]
----
static final class COWIterator<E> implements ListIterator<E> {
    private final Object[] snapshot; // незмінний snapshot масиву
    private int cursor;

    COWIterator(Object[] es, int initialCursor) {
        cursor = initialCursor;
        snapshot = es; // просто зберігаємо посилання — O(1), не копіюємо!
    }
    // set()/add()/remove() → UnsupportedOperationException
}
----

WARNING: Snapshot-ітератор — це *не копія даних*, а лише *посилання на старий масив*. Пам'ять старого масиву не звільняється, поки є живі ітератори, що тримають на нього посилання. При великих списках і довгих ітераціях це може призвести до підвищеного споживання пам'яті.

.Типовий сценарій використання — список слухачів (Listener pattern)
[source,java]
----
public class EventBus {
    // Ідеальний випадок: рідкісна реєстрація, часте сповіщення
    private final CopyOnWriteArrayList<EventListener> listeners = new CopyOnWriteArrayList<>();

    public void register(EventListener l)   { listeners.addIfAbsent(l); } // O(n) — але рідко
    public void unregister(EventListener l) { listeners.remove(l); }      // O(n) — але рідко

    public void publish(Event event) {
        // O(1) отримання snapshot-посилання + O(n) ітерація — часто, без блокувань
        for (EventListener l : listeners) {
            l.onEvent(event); // інші потоки можуть паралельно register/unregister
        }
    }
}
----

TIP: [[java-collection-framework-copyonwritearraylist-cowarrayset]]Якщо потрібна саме *множина* (без дублікатів) з тими самими гарантіями lock-free читання — подивись на `CopyOnWriteArraySet<E>`, який всередині обгортає `CopyOnWriteArrayList` і використовує `addIfAbsent()` для унікальності.

IMPORTANT: `CopyOnWriteArrayList` — вузькоспеціалізована структура. Використовуй її *виключно* коли: (1) читань на порядок більше ніж записів; (2) потрібна безпечна ітерація без зовнішньої синхронізації; (3) список відносно невеликий (копіювання великого масиву при кожному записі — дорого). Типові випадки: списки обробників подій, списки спостерігачів, конфігураційні списки, що читаються тисячі разів і змінюються раз на хвилину. Для протилежного профілю (часті записи, черга задач) шукай `ConcurrentLinkedQueue`/`ConcurrentLinkedDeque` — вони lock-free без копіювання всього вмісту на кожен запис.

[[java-collection-framework-copyonwritearraylist-pitfalls]]
.Підводні камені та нюанси

.Не для write-heavy сценаріїв — O(n²) при масових вставках
[source,java]
----
CopyOnWriteArrayList<String> list = new CopyOnWriteArrayList<>();
// Кожен add() копіює ВЕСЬ масив — O(n) на кожну операцію:
for (int i = 0; i < 10_000; i++) {
    list.add("item" + i); // 10 000 повних копій = O(n²) загалом!
}

// ПРАВИЛЬНО — збери у звичайний список, потім одним addAll():
List<String> temp = new ArrayList<>();
for (int i = 0; i < 10_000; i++) temp.add("item" + i);
list.addAll(temp); // ✅ лише ОДНА копія масиву
----

WARNING: Масові вставки у `CopyOnWriteArrayList` через цикл — це O(n²) операцій копіювання. Якщо потрібно додати N елементів — збери їх у `ArrayList`, потім виклич `addAll()`: це одна копія замість N.

.Ітератор — snapshot, не live view
[source,java]
----
CopyOnWriteArrayList<String> list = new CopyOnWriteArrayList<>(List.of("a", "b", "c"));
Iterator<String> it = list.iterator(); // фіксує snapshot: ["a", "b", "c"]
list.add("d");                         // список тепер ["a", "b", "c", "d"]
while (it.hasNext()) {
    System.out.print(it.next() + " "); // виводить: a b c — "d" НЕ видно!
}
----

NOTE: Snapshot-ітератор — це *feature*, не bug. Він гарантує консистентне читання без `ConcurrentModificationException`, навіть якщо список активно змінюється паралельно. Але будь готовий, що ітератор не бачить змін, які відбулись після його створення.

.Ітератор не підтримує remove()
[source,java]
----
CopyOnWriteArrayList<String> list = new CopyOnWriteArrayList<>(List.of("a", "b", "c"));
Iterator<String> it = list.iterator();
it.next();
it.remove(); // UnsupportedOperationException! — snapshot ітератор не підтримує мутацій

// ПРАВИЛЬНО — використовуй removeIf():
list.removeIf(s -> s.equals("a")); // ✅ атомарна операція під lock, одна копія масиву
----

WARNING: `Iterator.remove()`, `Iterator.set()` та `Iterator.add()` завжди кидають `UnsupportedOperationException` для `CopyOnWriteArrayList`. Для фільтруючого видалення використовуй `removeIf(Predicate)` — він виконує одну атомарну копію масиву для всіх видалень.

.Підсумки:
* Читання (`get`, `size`, ітерація) — O(1)/O(n) без жодного блокування, ідеально для read-heavy багатопотокових сценаріїв;
* Будь-яка мутація (`add`, `set`, `remove`, `sort`, `removeIf`...) — O(n), повна копія внутрішнього масиву під `ReentrantLock`;
* Ітератор — fail-safe snapshot, ніколи не кидає `ConcurrentModificationException`, але й не бачить змін після свого створення;
* `Iterator.remove()/set()/add()` завжди кидають `UnsupportedOperationException` — мутуй через методи самого списку, а не через ітератор;
* Масові вставки в циклі — антипатерн (O(n²)); завжди збирай у `ArrayList` і роби один `addAll()`;
* Не заміна для write-heavy черг — там доречніші `ConcurrentLinkedQueue`/`ConcurrentLinkedDeque` або `BlockingQueue`-реалізації;
* `RandomAccess` реалізовано по-справжньому: доступ за індексом лишається O(1), навіть попри "concurrent" у назві.
